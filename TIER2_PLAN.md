# Tier 2 Product Plan — TaxSabi Full System

Reference: `tax_advisor_implementation_plan.md` (13-section original blueprint).
Superseded for Gate 1 by `adtc_2026_project_plan.md` §6/§13 which deferred RAG to post-submission.

This plan restores the full architecture, with one correction: **Qdrant local mode is reinstated** — RAM headroom allows it.

## 1. Goal

Gate 1 proved the model. Tier 2 makes the *product* trustworthy: the LLM handles language, a versioned retrieval corpus and deterministic engine handle truth. No arithmetic is ever generated by the model.

## 2. Architecture

```
User input (En/Pidgin) → Language detection → LLM extraction (GBNF JSON)
                                              → Deterministic engine (chargeable income, tax, counterfactuals, unmentioned-relief flags)
                                              → Qdrant retrieval (grounding passages, filtered by year/jurisdiction)
                                              → LLM response (plain language, in user's language, citing retrieved text)
```

Core rule: LLM touches data at exactly two points (extraction in, phrasing out). All math lives in Python.

## 3. Retrieval — Decision

**Chosen: Qdrant local mode** (original doc §6 as specified)

```python
QdrantClient(path="./tax_corpus_db")  # disk-persisted, no server
# vectors: 384-dim, Distance.COSINE
# embedding via llama-server --embedding on a second port (nomic-embed-text Q4 or bge-small-en Q4)
```

Measured overhead: ~20–50 MB (Qdrant) + ~150–300 MB (embedding GGUF) + app overhead. Current model peak is ~1.71 GB. Total ~2.05 GB → well under the 7 GB budget (Seff ~70% vs ~76% now — ~5 point cost, acceptable). Original SQLite/JSON fallback remains documented if corpus stays tiny or embedding proves unstable, but **Qdrant is the default** per your call that headroom exists.

Why Qdrant now: semantic queries ("can I claim rent if I live with parents?") need similarity, not just keyword match. Corpus is small today (<50 chunks) but grows with multi-year support.

Corpus: one chunk per band/relief rule, with `jurisdiction`, `year`, `effective_from`, `superseded_on`, `superseded_by` — stature text stored verbatim from `sources/tax_act_2025.txt` for grounding.

Ingestion and retrieval exactly as in `tax_advisor_implementation_plan.md` §6.3–6.4.

## 4. Extraction — GBNF via llama.cpp

Grammar: `tax_extraction.gbnf` (gross salary, rent, pension, NHF, mortgage interest, life insurance, year=2026). Prompt enforces `null`/`false` for unstated facts — tested specifically. Served via `llama-server --grammar-file`.

## 5. Engine

Existing `src/rules_engine/` — unchanged. `get_active_ruleset(year, jurisdiction)`, `compute_chargeable_income`, `compute_tax` (per-band breakdown), `run_counterfactual`, `flag_unmentioned_reliefs`.

## 6. What Changes vs Gate 1

- Add second `llama-server` instance for embeddings (separate port; RAM-budgeted above)
- Ship Qdrant DB file inside the bundles (`tax_corpus_db/`) — no setup for user
- Desktop bundles updated to launch both servers; mobile path unchanged

## 7. Bundling

Tier 1 bundles already ship model + llama-server + HTML. Tier 2 adds:
- `tax_corpus_db/` (Qdrant local files, ~few MB)
- embedding GGUF (~80–150 MB Q4)
- Updated launchers that start both servers

Size impact: +~200 MB per platform bundle (still <1.2 GB total).

## 8. Validation

- Engine unit tests against BizEdge worked example (₦3.6M gross → ₦359,160) — already passing
- Extraction accuracy on Pidgin/Yoruba/Hausa/Igbo phrasings (critical path)
- Full-pipeline E2E: extraction → engine → retrieval → response, then `adtc-profiler` full run with both models resident

## 9. Roadmap
